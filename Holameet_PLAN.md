## 1. О ПРОЕКТЕ

**Название:** Holameet
**Суть:** Сервис бронирования встреч по персональной ссылке — локализованный
аналог Calendly, сделанный **специально для украинского рынка**.

**Целевая аудитория (MVP):** украинские специалисты, которые часто назначают
встречи с клиентами — репетиторы, коучи/психологи, консультанты-фрилансеры
(юристы, бухгалтеры, маркетологи), рекрутеры небольших IT-компаний.

**Ключевое отличие от Calendly:**
- Интерфейс полностью на украинском языке.
- Уведомления и подтверждения через **Telegram**, а не только email — потому
  что рабочая коммуникация в Украине живёт в Telegram.
- Часовой пояс по умолчанию — Europe/Kyiv.
- В будущем (не MVP) — оплата через LiqPay/Monobank вместо Stripe.

**Ценностное предложение одной фразой:** убрать переписку "когда тебе
удобно?" — отправляешь ссылку, человек сам выбирает слот, встреча падает
в календарь автоматически.

---

## 2. СТЕК

- Frontend: React + TypeScript + Tailwind CSS
- Backend: Node.js + Express + REST API
- База данных: PostgreSQL
- Очереди задач: BullMQ + Redis (напоминания)
- Интеграции: Google Calendar API (OAuth2), Telegram Bot API
- Инфраструктура: Docker + docker-compose
- Тесты: Vitest (unit), Playwright (только для критичных e2e-флоу)

## 3. ПРАВИЛА РАБОТЫ АГЕНТА (обязательны на всех фазах)

1. **Работаем строго по фазам.** Не пиши весь проект сразу. После каждой фазы

   больше — сам разбей её на подзадачи и предупреди меня заранее.
3. **Зависимости:** перед установкой любого нового npm-пакета — спроси меня
   и объясни, зачем он нужен и нет ли решения без новой зависимости.
4. **Секреты:** все ключи/токены только через `.env` (в `.gitignore`).
   Всегда поддерживай актуальный `.env.example` с пустыми плейсхолдерами.
5. **Локализация — не опция, а требование с первого дня:** все тексты
   интерфейса на украинском, вынесены в отдельный файл переводов (даже если
   английского пока не будет — так проще добавить позже).
6. **Критичные зоны кода** (см. раздел 6) — обязательно объясни логику
   ДО написания кода и явно перечисли учтённые edge-кейсы.
7. **Контракт API:** перед фронтендом, который дёргает backend — зафиксируй

8. Не генерируй код "про запас" сверх нужного для текущей фазы.
9. **Критерии готовности фазы** — в конце каждой фазы дай чеклист вида
   "фаза готова, если: 1)... 2)... 3)..." — конкретно и проверяемо.
10. Для критичных мест — пиши unit-тесты сам, не дожидаясь просьбы.
11. **Сигнал неуверенности:** если не уверен в поведении внешнего API или
    в решении — прямо скажи "здесь не уверен, предлагаю проверить так: ...".
12. После каждой завершённой и протестированной фазы — напомни сделать
    `git commit` с понятным сообщением, прежде чем идти дальше.
13. Если моя просьба скрывает архитектурную проблему на будущее — скажи

## 4. ФАЗЫ РАЗРАБОТКИ

### Фаза 0 — Настройка проекта
- Структура папок (`frontend/`, `backend/`, `shared/`).
- `docker-compose.yml` (Postgres + Redis).
- Базовые `package.json`, ESLint + Prettier, `.env.example`.
- **Спроси меня:** монорепо или два репозитория; куда планирую деплоить.

**Готово, если:** проект поднимается одной командой (`docker-compose up`),
линтер настроен и проходит на пустом проекте.

---

### Фаза 1 — Схема базы данных
Таблицы:
```
users (id, email, password_hash, name, timezone default 'Europe/Kyiv',
       working_hours_json, buffer_minutes, created_at)

event_types (id, user_id, title, slug, duration_minutes, is_active)

bookings (id, event_type_id, invitee_name, invitee_email, invitee_tz,
          start_time_utc, end_time_utc, calendar_event_id, status,
          created_at)

calendar_connections (id, user_id, provider, access_token_encrypted,
                       refresh_token_encrypted, expires_at, is_valid)
```
- Объясни каждое поле и связи. Дождись моего "ок" перед миграциями.

**Готово, если:** миграции применяются и откатываются без ошибок,
есть `UNIQUE constraint` на `(event_type_id, start_time_utc)` в bookings.

---

### Фаза 2 — API-контракт (shared/types.ts)
- Опиши все запросы/ответы для фаз 3-8 заранее, прежде чем кодить
  реализацию.

**Готово, если:** типы покрывают все эндпоинты из последующих фаз,
frontend и backend импортируют один и тот же файл типов.

---

### Фаза 3 — Auth и профиль пользователя
- Регистрация/логин (email + пароль, хэш через bcrypt).
- CRUD настроек доступности (рабочие часы, буферы, часовой пояс).
- UI на украинском языке.

**Готово, если:** можно зарегистрироваться, залогиниться, сохранить рабочие
часы, и это переживает перезапуск сервера (данные в БД, не в памяти).

---

### Фаза 4 — Логика доступности и бронирования 🔴 КРИТИЧНАЯ ФАЗА
- Все временные метки только в UTC в базе данных.
- Конвертация в локальное время — только на отображении.
- Создание бронирования — атомарно через `UNIQUE constraint`,
  никогда через "проверить, потом записать" (race condition).
- **Обязательные unit-тесты:**
  - переход на летнее/зимнее время (украинский и минимум один зарубежный
    часовой пояс);
  - попытка забронировать уже занятый слот;
  - одновременное бронирование одного слота двумя запросами.

**Готово, если:** все тесты выше проходят, и вручную проверено бронирование
из двух разных часовых поясов в браузере (эмуляция через DevTools).

---

### Фаза 5 — Интеграция Google Calendar
- OAuth2 flow (подключение аккаунта из личного кабинета).
- `freebusy.query` — синхронизация занятости, включая события, созданные
  пользователем вручную (не только через Holameet).
- Шифрование токенов at rest (отдельный секрет, не тот же, что для сессий).
- Обработка истёкшего/отозванного токена — статус "переподключите календарь"
  в UI, а не тихий сбой.
- **Распиши мне все сценарии ошибок до написания кода.**

**Готово, если:** отключение доступа в настройках Google корректно
отображается в UI Holameet, а не роняет приложение с 500 ошибкой.

---

### Фаза 6 — Публичная страница бронирования (frontend)
- `holameet.com/u/:username/:eventSlug`.
- Календарная сетка слотов, автоопределение часового пояса гостя
  через `Intl.DateTimeFormat().resolvedOptions().timeZone`.
- Форма для имени/email гостя + чекбокс согласия на обработку данных.
- Полностью на украинском языке.

**Готово, если:** гость без аккаунта может забронировать слот от начала
до конца, событие появляется в Google Calendar организатора.

---

### Фаза 7 — Личный кабинет (frontend)
- Список типов встреч, создание/редактирование.
- Список предстоящих бронирований.
- Базовая статистика (сколько встреч забронировано за период).

**Готово, если:** пользователь может полностью настроить профиль без
обращения к backend напрямую (только через UI).

---

### Фаза 8 — Telegram-бот
- Подключение бота через deep link из личного кабинета.
- Подтверждение бронирования организатору и гостю (если у гостя есть Telegram).
- Напоминания за 24ч и за 1ч до встречи — через задачи BullMQ
  с точным временем выполнения, НЕ через периодический скан всей таблицы.
- Задачи должны быть идемпотентны (повторный запуск не шлёт напоминание дважды).

**Готово, если:** тестовое бронирование с коротким временным окном (например,
через 2 минуты) реально присылает напоминание один раз.

---

### Фаза 9 — Деплой и чеклист запуска
- Верификация Google OAuth consent screen (может занять 1-2 недели — начать
  параллельно с Фазой 5).
- Проверка, что нигде в коде/git-истории нет секретов.
- Настройка бэкапов PostgreSQL.
- Базовый мониторинг ошибок (Sentry или аналог).
- Privacy Policy на украинском (обработка данных гостей).

**Готово, если:** можно провести полный цикл (регистрация → подключение
календаря → публичная ссылка → бронирование гостем → напоминание в Telegram)
на проде без ошибок.

## 5. НЕ ВХОДИТ В MVP (явно откладываем)

- Оплата (LiqPay/Monobank) — добавим после первых живых пользователей.
- Командные аккаунты / несколько участников на одну встречу.
- Встраиваемый виджет (embed) на сторонние сайты.
- Мобильное приложение.
- Английская локализация.

Если агент предлагает начать что-то из этого списка раньше времени —
он должен спросить, а не делать молча.

---

## 6. КРИТИЧНЫЕ ЗОНЫ КОДА (правило действует на любой фазе)

Всегда объяснять логику до написания кода и явно указывать edge-кейсы:
- Даты, время, часовые пояса.
- Создание/изменение бронирования (конкурентный доступ).
- OAuth-токены и любые чувствительные учётные данные.
- Всё, что касается персональных данных гостей (не только зарегистрированных
  пользователей).

---

## 7. МЕТРИКА УСПЕХА MVP

Не количество регистраций, а: **% пользователей, отправивших хотя бы одну
ссылку бронирования реальному клиенту в течение первой недели.** Если этот
процент низкий — проблема в онбординге, а не в фичах, и чинить нужно её
раньше, чем добавлять новый функционал.
